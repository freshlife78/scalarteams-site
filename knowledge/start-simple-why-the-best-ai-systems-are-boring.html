Start simple: why the best AI systems are boring

Published October 31, 2026 by Scalar Teams

There is a widespread assumption that serious AI means autonomous agents making decisions on their own. The people who build these systems for a living say otherwise. In December 2024, Anthropic published engineering guidance based on its work with teams building AI systems across industries, and its central message is unglamorous: keep it simple, and add complexity only when you can prove you need it.

Two kinds of system

Anthropic’s post, “Building effective agents,” begins by separating two things that often get the same label. A workflow is a system where a language model and tools are orchestrated through code paths the developer wrote in advance. The model does a defined job at a defined step. An agent is a system where the model directs its own process and decides which tools to use and in what order.

The authors’ advice on choosing between them is direct. Workflows suit well-defined tasks where predictability matters. Agents are the better option when flexibility and model-driven decision-making are needed at scale, and when you can accept higher cost and latency in exchange. For most operational work in a mid-sized company, the first description fits far more often than the second.

The core recommendation

The post recommends “finding the simplest solution possible, and only increasing complexity when needed.” The reasoning is practical rather than philosophical. Agentic systems trade latency and cost for better performance on hard problems, and that trade only makes sense when the problem is genuinely hard. The authors say many applications need nothing more than a single well-constructed call to a model, with good examples and relevant documents retrieved for it.

They are also cautious about frameworks, the software packages that promise to make agent-building easy. Frameworks help teams start quickly, but their extra layers can hide the actual prompts and responses underneath, which makes problems harder to diagnose. Their suggestion is to start with the model’s API directly and, if a framework is adopted later, to understand the code under it before relying on it.

Five boring patterns that work

Most of the post is a catalogue of workflow patterns the authors have seen succeed. In plain terms:

  • Prompt chaining. Break a task into a sequence of steps, each handled by a model call, with a programmatic check between steps. Example: extract the fields from a supplier invoice, then check the totals add up, then draft the posting.
  • Routing. Classify an input first, then send it to the specialized handler for that type. Example: sort incoming emails into orders, claims and general enquiries before anything else happens.
  • Parallelization. Run independent subtasks at the same time, or run the same task several times and compare the answers. Useful when you want a second opinion on a high-stakes extraction.
  • Orchestrator and workers. One model breaks a job into parts, hands the parts to workers, and assembles the results. Reserved for tasks where the parts cannot be known in advance.
  • Evaluator and optimizer. One model produces a draft, another critiques it, and they loop until the draft passes. Useful where there are clear criteria for “good,” such as a translation or a formatted report.

Notice what these have in common. Each has a shape you can draw on a whiteboard, a place where a human or a rule can check the work, and a failure mode you can name. That is what “boring” means here, and it is a compliment.

When an agent is warranted

The authors do not dismiss agents. They describe them as appropriate for open-ended problems where the number of steps cannot be predicted and a fixed path cannot be written, and they stress that agents need the ability to get feedback from their environment, such as a test result or a tool’s output, at each step. The two examples they give are customer support, where the conversation flow is combined with tools that fetch order history and take actions like issuing refunds, and software coding, where automated tests give the agent an objective signal about whether its work is correct. Both examples share a feature: success is checkable.

For agents, the post offers three principles. Keep the design simple. Make the agent’s planning steps visible so people can see what it intends to do. And invest heavily in the interface between the agent and its tools, documenting and testing each tool as carefully as you would for a new employee.

A note on timing

The post is dated December 19, 2024, and Anthropic itself now notes that much of the tooling has changed since then and points readers to newer documentation. The specific tools will keep changing. The argument about simplicity is about engineering discipline, and it has not aged.

How we apply this

Our method borrows from the Toyota Production System, so we read research like this as a checklist for practice rather than a forecast. In order, the steps are: go and see, map, measure waste, prioritize, build small, standardize and review.

Anthropic’s guidance and the Toyota method agree on the same point from different directions: do not automate what you do not yet understand. We go and see the task, map the real sequence of steps, and measure where the waiting and rework are. That map usually turns out to be a workflow in Anthropic’s sense, a fixed path with a few decision points, and we build it that way: one step at a time, a check between steps, a person in the loop wherever money moves or a customer is affected.

We build small, which here means a single model call before a chain and a chain before anything autonomous. We standardize by writing down the prompts, the checks and the escalation rules so the system is inspectable by your team, not just by us. And we review the failure cases on a schedule, because the boring system that is watched outperforms the clever one that is not.
