What We Learned from a Year of Building with LLMs (Applied Engineering Survey)

Synthesizing lessons across hundreds of real-world deployments, six veteran AI practitioners—Eugene Yan, Bryan Bischof, Charles Frye, Hamel Husain, Jason Liu, and Shreya Shankar—documented the operational habits that separate durable production LLM systems from fragile demos.

CTO Vetting Takeaway

We use the tactical practices in this field guide as a blueprint when interviewing senior AI engineering candidates—specifically testing whether candidates inspect raw failure traces, exhaust retrieval + in-context learning before fine-tuning, and design verification-first UX.

Lesson 1: Look at Your Data Every Single Week

The single highest-leverage habit among successful AI engineering teams is simple yet surprisingly rare: regularly reading raw production inputs, intermediate retrieval chunks, and model outputs. Teams that rely exclusively on aggregate dashboard metrics miss obvious failure modes—such as broken PDF table parsers, truncated context windows, or users asking questions in a language or format the prompt never anticipated.

Senior engineers build lightweight trace-inspection views so product managers, domain experts (CPAs, clinicians, lawyers), and engineers can review 50 real production traces a week and categorize failure clusters.

Lesson 2: Exhaust Prompting, Few-Shot Examples, and RAG Before Fine-Tuning

Inexperienced teams often propose fine-tuning an open-weight or proprietary model as their first solution to accuracy problems. The Applied LLMs authors warn strongly against premature fine-tuning:

  • If the model lacks domain facts: Fine-tuning is the wrong tool for injecting rapidly changing company data (such as current inventory prices, customer contracts, or updated tax rules). Improve your RAG pipeline (hybrid search, metadata filtering, contextual chunking) instead.
  • If the model fails formatting or edge-case reasoning: Dynamic few-shot prompting—retrieving the 3–5 most similar gold-standard input/output examples from a verified bank and injecting them into the prompt—frequently matches or beats fine-tuning without locking you into a deprecated model checkpoint.
  • When fine-tuning actually makes sense: Only after prompting and RAG are exhausted, and usually to distil the behavior of a slow, expensive frontier model into a smaller, low-latency model for a narrow, high-volume task.

Lesson 3: Design User Interfaces Around Verification Speed

Because LLMs remain probabilistic, the user interface must make human verification effortless. Rather than presenting a wall of generated text and forcing the user to cross-check a 40-page PDF manually, production interfaces:

  • Render extracted fields right next to the source document with highlighted bounding boxes showing the exact line where each number came from.
  • Provide keyboard-driven Approve / Edit / Reject workflows so a human operator can verify 60 records an hour—while every human edit automatically logs a gold-standard training pair.

Lesson 4: Defensive Guardrails & Input/Output Isolation

Production systems assume user inputs and external documents are untrusted. Mature architectures combine input guards (PII masking, prompt-injection detection, scope filters) with strict output validation and least-privilege tool execution so a malformed or adversarial document cannot trigger unauthorized downstream actions.
